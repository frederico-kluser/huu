- [2026-07-03][source:inference][task:kanban-done-means-merged][probation] mergeAgentBranches gained an optional 4th param onBranchMerged?: (branchName) => void, fired right after each branch lands (also threaded through the resolver path via IntegrationContext.onBranchMerged, including the post-resolver verification loop's three merge-success sites) — the orchestrator uses it to flip per-card merged flags AS the ascending merge progresses. - [2026-07-28][source:inference][task:dev-mode][probation] CHAINING RUNS needs an explicit landing step. A run accumulates on `huu/<runId>/integration` and `start()`'s finally REMOVES the integration worktree while leaving the BRANCH for the user to merge later. Correct for a one-shot pipeline; fatal for a chain, because run N+1 does `runPreflight(cwd)` and branches its integration worktree from the USER'S CHECKOUT head — so without an explicit merge, every later run re-plans against pre-run-1 code and run N's work sits orphaned. `src/lib/dev-mode/epoch-landing.ts` is the pattern: guard branchExists → guard a clean tree (`hasChanges`) → `merge --no-ff` → on failure `abortMerge` and report conflicts (never leave a half-merged tree; it blocks the NEXT run and confuses the user). Never throws — every failure comes back as `{landed:false, error}`.
- [2026-07-28][source:inference][task:dev-mode][probation] `Orchestrator.start()` DIRTIES the user's working tree: `ensureGitignored` writes `.huu-worktrees/`, the run-log dir, `.env.huu` and the agent bin dir into `.gitignore` (creating the file on a repo that never ran huu). Any driver that merges between runs must COMMIT that housekeeping BEFORE the merge, or the clean-tree guard refuses. Found by the first end-to-end dev-mode session, not by any unit test — the fixture repos had no `.gitignore`. Pinned by `dev-driver.test.ts` "sweeps huu-written .gitignore changes before landing".
- [2026-07-28][source:inference][task:dev-mode][probation] `GitClient.getChangedFiles` TRUNCATED the first path (fixed 2026-07-28, `git-client.test.ts`): it did `stdout.trim()` before splitting, which strips the leading space of the FIRST line only, and `parsePorcelainPath`'s fixed `slice(3)` then ate that path's first character (`alpha.txt` → `lpha.txt`). Porcelain status codes are TWO columns and an UNSTAGED modification is `" M "`, so the common case always hit — `AgentStatus.filesModified` misreported the first file on every card. General rule: never `trim()` porcelain output before splitting it; trim per line. For a plain dirty-path check prefer `diff --name-only HEAD` + `ls-files --others --exclude-standard`, which emit bare paths with no status prefix at all.
