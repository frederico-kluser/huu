- [2026-07-01][source:inference][task:dogfood-angular-react-multirun][probation] A CheckStep judge run with a WEAK model (openai/gpt-4o-mini) emitted no parseable verdict JSON, so huu logged "judge produced no parseable verdict; using default outcome" and took the `default: true` outcome. With the recommended-safe pattern `default: approved`, that means the judge SILENTLY RUBBER-STAMPS — it never actually gates. In a real Angular→React refactor this let genuine defects through (empty `dependencies` in package.json, a missing `<script src=main.jsx>` entry so the app never mounts, an invalid 7-digit hex color). Lessons: (a) give judge/CheckStep steps a capable model (`modelId` override on the step) — the verdict-JSON discipline is exactly where small models fail; (b) keep the `condition` mechanically checkable so even a weak judge can comply, and consider making the loop-back (`rework`) the more likely path when unsure; (c) NEVER trust a green judge as proof — inspect the diff yourself. The judge's forward-default is a safety valve against infinite loops, not evidence the work is correct.

- [2026-07-28][source:inference][task:dev-mode][probation] `scope: 'memory'` fan-out over NON-FILE work units: `resolveMemoryFiles` DROPS any listed path that does not exist in the integration worktree (and throws when a non-empty list resolves to zero). So a step that fans out over abstract units (tasks, findings, migrations) cannot list intended targets — the producer must MATERIALIZE one real file per unit and list those. Dev mode does exactly this: the front recon writes `.huu/dev/epoch-N/<front>/T-001.md` (a full task briefing) plus the huu-memory-v1 list pointing at the spec files; `$file` is then the spec path and `$hint` its one-line summary. Bonus, not a workaround: the plan ends up version-controlled and auditable in the diff.
- [2026-07-28][source:inference][task:dev-mode][probation] A pipeline can be GENERATED at run time and still be first-class: `compileEpochPipeline` (src/lib/dev-mode/plan-to-pipeline.ts) emits a `dependsOn` graph and validates it with the SAME `PipelineSchema.safeParse` a hand-authored file goes through, so a compiler bug fails loudly instead of producing a subtly wrong run. Two compiler-owned invariants an LLM planner must never be trusted with: (a) `dependsOn` may only name EARLIER steps — emit fronts in TOPOLOGICAL order and break a cycle by DROPPING edges with a warning rather than failing the run; (b) each check's single `default:true` must point FORWARD (it fires on judge failure / unknown label / maxRuns cap) while `rework` points backward. Test the compiled graph against the REAL `computeWave`/`validateTopology`, not a mock — that is what proves independent branches land in one wave.
- [2026-07-28][source:inference][task:dev-mode-v2][probation] `WorkStep.review` (`ReviewSpec` in types.ts, `ReviewSpecSchema` in pipeline-io.ts) is public pipeline schema, not a dev-mode private: any work step in any pipeline may declare a per-task generator→critic loop that audits each agent's diff IN ITS OWN WORKTREE before the branch is eligible for the stage merge. It is deliberately absent from `CheckStepSchema` — a check already IS a judge, runs post-merge in the integration worktree, and would have no worktree to audit nor agent to send findings back to (an unknown key there is dropped on parse, so it can never reach the orchestrator). Fields: `prompt` (required), `maxRounds` (1-4, default 2), `blockOn` (non-empty severity list, default `['blocker','major']`), `modelId`, `timeoutMs`, `maxFindings` (1-50, default 10), `verifyCommands`, `findingsDir`. The bounds are safety rails: an empty `blockOn` is a loop that can never converge, and each round costs a full extra agent turn, so a reviewed card can take `cardTimeout × (1 + maxRounds)` of wall clock. Rounds are intra-step and do NOT consume `maxNodeExecutions`.
- [2026-07-28][source:inference][task:dev-mode-v2][probation] Two `review` semantics to design around, both counter-intuitive. (a) CONVERGENCE IS BY SEVERITY, not by the critic's words: the loop repeats while any finding's severity is in `blockOn`; the emitted `"verdict"` string is logged and ignored, so "approved" over a blocker still loops and "changes-requested" over three nits does not — the same fixed-enum mechanical-judge rule check conditions already follow. (b) EVERY FAILURE IS FORWARD-DEFAULT — THE WORK MERGES: critic threw / timed out / was abandoned / emitted nothing parseable ⇒ verdict `unavailable` ⇒ zero blocking; a failed fix turn ⇒ waive; the round cap with blockers still open ⇒ WAIVE, record, merge. Failing the card instead would make `runStageIntegration` drop the branch and convert "90% right with one major finding" into nothing. So never design a pipeline that RELIES on `review` to guarantee something — it raises the floor and produces a machine-readable finding list (`findingsDir` shards, one `agent-<N>.json` per task, `"waived": true` when they got through). When you need a hard stop or routing, that is still a `CheckStep`.
