- [2026-07-28][source:inference][task:dev-mode-v2][probation] `compileKnowledgePipeline` emits THREE steps, not the two the design called for, and the extra one is not padding: `validateTopology` rejects a `memory`-scope step at index 0 (no earlier step could have written its memory file) and cannot tell that huu wrote and COMMITTED the index in TypeScript before the run. So K0 "Preparar o quadro" exists anyway and takes the one job the run genuinely needs first — the PERSISTENCE CHECK: in a repo whose `.gitignore` excludes `.huu/`, every brief would be silently dropped from its agent's commit, the wave would merge nothing, the digest would consolidate nothing, and the blind orchestrator would plan the next epoch on an empty file with no error to show. Phase A also has NO CheckStep on purpose: a judge would cost an agent per epoch to protect one file, and `readKnowledgeDigest`'s deterministic fallback to the raw brief shards covers the same failure for free. Every path out of Phase A is forward.
- [2026-07-28][source:inference][task:dev-mode-v2][probation] Zero knowledge gaps is a DECISION, not a defect: `KnowledgeRequestSchema.gaps` defaults to `[]` and an empty array means "I already know enough", so the driver skips Phase A entirely and the epoch is one run, exactly as it always was. Do not "fix" it by retrying the planner or by manufacturing a request from `BASELINE_GAPS` — the baselines are a FLOOR UNDER A REQUEST that was actually made (`mergeBaselineGaps` is only called when `gaps.length > 0`), and the empty path is also what keeps a `--stub` session at one run per epoch, since the stub backend cannot answer a question (it writes no files). Corollary for `--stub` in general: the memory fan-out resolves to ZERO tasks, so the swarm AND the review loop never execute — it proves wiring, never work.
- [2026-07-28][source:inference][task:dev-mode-v2][probation] Session namespacing (`.huu/dev/<sessionId>/…`) is a correctness fix, not tidiness. `resolveMemoryFiles` reads `filesFrom` from the INTEGRATION worktree, which branches from the user's checkout — and after any earlier session landed, that checkout contains a COMMITTED `.huu/dev/epoch-1/<frontId>/tasks.json`. It also does no validity check at all, only `existsSync`. Front ids are semantic (`api`, `cli`, `tests`), so a new session whose recon failed or wrote fewer specs would fan out over the PREVIOUS session's task list, silently. A path segment makes that impossible rather than improbable. Two things ride along: `DEV_STATE_FORMAT` is `huu-devstate-v2` and `readDevState` returns `null` on a foreign `_format`, so a v1 file degrades to "no resume" with zero migration code; and resume defaults to NO when no callback is wired, which is what keeps every pre-existing caller byte-identical.

- [2026-08-01][source:inference][task:dev-harness-audit][probation] Knowledge does NOT accumulate across epochs and the digest has no correctness path: `readKnowledgeDigest(cwd, paths, epoch)` reads ONLY the current epoch, `BASELINE_GAPS` fire only on epoch 1 (replaced by `DELIVERED_VS_PLANNED_GAP` afterwards), and the only fact that survives in `DevState` is `verifyCommands` — so by epoch 3 the blind planner knows LESS about the repo than it did at epoch 1. The digest fallback to raw brief shards triggers only when the digest is ABSENT/EMPTY, never when it is WRONG, and it is written by ONE unrestricted agent. But `KnowledgeBriefSchema` already validates every shard (gapId/kind/confidence/answer/facts/sources/unknowns), so the digest could be ASSEMBLED IN TYPESCRIPT with deterministic budget truncation and the LLM pass demoted to optional refinement — which is the project's own "model writes CONTENT, huu writes STRUCTURE" doctrine (`knowledge-schema.ts` header) applied at the one point in the flow where it is currently violated. `KNOWLEDGE_DIGEST_MAX_CHARS = 6000` over up to `DEV_MAX_GAPS = 12` gaps (~500 chars/gap) is not derived from the planner model's context window — it is an unmeasured constant.
- [2026-08-01][source:inference][task:dev-harness-waves][probation] IMPLEMENTED the audit's four waves; three corrections to what the audit itself claimed, all found only by opening the SDK. (1) `createAgentSessionOptions.tools?: string[]` is an allowlist of NAMES (`read|bash|edit|write|grep|find|ls`; default active = the first four) and a HARD filter — `agent-session.js` drops non-listed tools from the registry AND rebuilds the system prompt from the survivors, so the model is not told they exist. `pi`'s own `createReadOnlyTools` preset is read+grep+find+ls (NO bash), which is why huu spells its own list out: the critic and the judge MUST keep `bash` to run the project's gate. (2) A19 in the audit ("no tool-result budget") is WRONG — pi truncates at `DEFAULT_MAX_LINES = 2000` / `DEFAULT_MAX_BYTES = 50KB`, bash tail-truncates and offloads the full output to a temp file, read head-truncates and tells the model to paginate. The real gap is that `grep`/`find`/`ls` exist and are NOT enabled, so every agent shells out — but enabling them for writing agents is a capability EXPANSION that changes every existing pipeline's system prompt with no option set, so it was deliberately NOT shipped inside the restriction change. (3) A13's token saving is ~0: `agents-md-generator` runs BEFORE the step prompt and carries agentId/stageName/files, so the cross-agent shared prefix is `"# Agent "`. Ship the fixed-first ordering as a structural invariant with a pinning test, never as a cost saving.
- [2026-08-01][source:inference][task:dev-harness-waves][probation] `/skill:<name>` in a pi prompt has a SECOND precondition nobody had noticed: `_expandSkillCommand` (`core/agent-session.js`) returns the text untouched unless it STARTS with `/skill:` — and huu's role header always precedes the step prompt, so the token was never in position 0 even before `noSkills` was considered. The fix that DOES work is `additionalSkillPaths`: `resource-loader.js` merges it in EVEN WHEN `noSkills: true` (`noSkills ? mergePaths(cliEnabledSkills, additionalSkillPaths) : …`), so worktree-scoped skills load without reopening the ancestor walk or `~/.pi`. pi then renders them into the system prompt as `<available_skills>` (name + description + path) with "use the read tool to load a skill's file" — progressive disclosure, which is what the huu skill library was designed for.
- [2026-08-01][source:inference][task:dev-harness-waves][probation] `readOnly` must NOT be applied to dev mode's report steps. The plan auditor writes `plan-review.md` + a findings shard, consolidate writes the epoch report, seal appends the journal, K2 writes the digest — strip `write` from any of them and the step produces nothing, the gate that reads its output routes to `rework`, and the epoch loops to `maxRuns`. Only the critic (`review-agent.ts`) and the judge (`check-evaluator.ts`, CHECK_AGENT_ID) are genuinely reply-only. Same shape of trap as any "harden the boundary" change here: the boundary is real, the tool is load-bearing.
- [2026-08-01][source:inference][task:dev-harness-waves][probation] A validation tier that cannot REPLACE what it rejects must not reject it. First cut of the digest tiering discarded an LLM digest whenever `digestMissingGaps` found a hole, and `dev-driver.test.ts:911` went red instantly: with no brief shards to assemble from, the planner got `undefined` instead of the repo digest — a partial answer turned into none. The shipped order is: complete digest → mechanical assembly from validated shards → the INCOMPLETE digest with the uncovered gap ids named → raw shards. Same rule as the rest of dev mode, one level down, and the test that caught it is the one worth keeping.
