# Internationalization

O huu vem em **inglês** (`en`, o padrão) e **português do Brasil** (`pt-BR`).
As duas interfaces — a TUI de terminal em Ink e a UI do navegador — leem o mesmo
catálogo, e o `--help`, os banners e os erros do CLI também.

## Picking the language

| Superfície | Como |
|---|---|
| CLI + TUI de terminal | `HUU_LANG=pt-BR huu` — ou `HUU_LOCALE`, ou a cadeia POSIX `LC_ALL` → `LC_MESSAGES` → `LANG` |
| UI web | ⚙ **Configurações → Idioma**. Salvo por navegador em `localStorage` (`huu.lang`); trocar repinta a página sem recarregar |

Qualquer coisa não reconhecida cai em `en`. `pt`, `pt-PT` e `pt_BR.UTF-8` viram
`pt-BR`; `en-GB` e `en_US.UTF-8` viram `en`.

## A missing translation is an error, on purpose

O contrato é que o huu nunca renderiza uma tela meio traduzida. Isso é imposto
em três camadas, então um buraco não chega ao usuário:

1. **Tempo de compilação.** `en` é o catálogo fonte: as chaves dele definem
   `MessageKey`, e `pt-BR` é tipado como `Record<MessageKey, string>`. Adicione
   uma chave em `en` sem a gêmea e `npm run typecheck` falha, nomeando a chave.
2. **Boot.** Todo entrypoint chama `initI18n()`, que roda
   `assertCatalogsComplete()`. Uma chave ausente, vazia, órfã, ou cujos
   `{placeholders}` divergiram entre os locales aborta o processo com
   `CatalogIntegrityError` antes do primeiro frame.
3. **Ponto de chamada.** `t()` e `translate()` lançam `MissingTranslationError`
   no instante em que a chave falta em **qualquer** locale — inclusive um que o
   usuário não está usando. Uma chave só-em-inglês não pode sobreviver só porque
   ninguém trocou para `pt-BR`.

Além disso, `src/lib/i18n/coverage.test.ts` varre o código, coleta toda chave que
a aplicação referencia e reprova a suíte diante de uma referência sem tradução ou
de uma chave órfã no catálogo.

**Válvula de escape:** `HUU_I18N_STRICT=0` rebaixa as camadas 2 e 3 para um aviso
em stderr e renderiza a chave crua. Existe para quem prefere entregar uma string
tosca a parar; o padrão é estrito.

## Adding a key

1. Adicione no módulo certo em `src/lib/i18n/locales/en/` — `common.ts` (verbos
   compartilhados, códigos de status), `cli.ts`, `tui.ts`, `tui-run.ts`,
   `tui-editor.ts` ou `web.ts`.
2. Adicione a mesma chave na gêmea `pt-BR`. O `npm run typecheck` avisa se você
   esquecer.
3. Use:
   - **TUI / CLI / servidor** — `import { t } from '../lib/i18n/index.js'`, e
     então `t('tui.home.menu_quit')`. A chave é tipada, então um typo vira erro
     de build.
   - **JS do navegador** — `import { t } from '../i18n.js'`, mesma chamada.
   - **Markup do navegador** — `data-i18n="web.settings.title"` no elemento
     (também existem as variantes `-html`, `-placeholder`, `-title`,
     `-aria-label`).
4. Interpole com slots `{name}`: `t('tui.dash.retry_prompt', { id: 7 })`. Um slot
   sem parâmetro correspondente lança `MissingParamError`.

Para uma chave montada em tempo de execução (`status.${code}`), use `translate()`
— mesmas garantias, sem checagem em tempo de compilação — e registre o prefixo em
`DYNAMIC_PREFIXES` dentro de `coverage.test.ts` para a checagem de órfãs continuar
honesta.

## What is deliberately NOT translated

- **Dados de pipeline.** Os nomes e prompts dos passos gerados pelo editor vão
  para uma LLM, não são chrome. Ficam em inglês para um pipeline se comportar
  igual, seja qual for o idioma da UI de quem o escreveu.
- **Códigos do classificador.** `src/lib/card-state.ts` e o espelho de navegador
  `src/web/client/card-state.js` devolvem códigos estáveis em inglês
  (`NO CHANGES`, `READY`). São puros, espelhados e travados por testes; a
  tradução acontece na fronteira de renderização, via `tStatus()` (Ink) e
  `phaseLabel()` (web).
- **Nomes de marca e de protocolo.** `OpenRouter`, `Azure AI Foundry`, `git`,
  `worktree`, nomes de variáveis de ambiente, flags do CLI.
