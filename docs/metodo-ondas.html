O diagnóstico medido do método de desenvolvimento do huu, e um plano de 34 ações em 11 ondas para fechar o que a documentação já promete e o código ainda não garante.

A resposta, numa frase

O huu é excelente em tornar o método determinístico e quase não investiu em tornar a verificação falsificável.

Cada uma das quatro famílias de lacuna abaixo é essa mesma frase em outro domínio. Nenhuma delas é sobre orquestração — o BSP sobre git funciona e está provado em dogfooding. Todas são sobre verificação, propriedade de arquivo e proveniência.

As quatro famílias

O achado mais grave do repositório tem uma linha. A cláusula 4 do juiz compartilhado das 5 auditorias usa git status --porcelain — e o próprio código do huu, 100 arquivos ao lado, explica por que ela nunca pode falhar:

“the stage merges are already committed by the time the judge runs, so a bare git status is clean” — check-evaluator.ts:19-22

Consequência exata: o contrato report-only de 5 dos 7 pipelines default — a promessa de que uma auditoria não toca seu código — é verificado por um comando que não consegue reprovar. A forma correta existe um arquivo ao lado (huu-test-suite.ts:343) e $baseCommit já é substituído. É uma linha. Ver a aba Falso-verde para os outros 22 casos.

docs/dev-mode.md:250-253 traz um cabeçalho literal: “Rules huu enforces (that the planner cannot break)” — Partition by file ownership.

Nada enforça isso. A busca foi exaustiva e negativa: prepareStageTasks e decomposeTasks não comparam caminho entre tasks; não há lock, não há teste de disjunção, não há checagem pré-merge. O isolamento é de worktree — impede pisar em tempo real, não impede o merge limpo que integra código contraditório. O que existe diz de si mesmo:

“PURE INSTRUMENTATION — nothing is blocked, reverted or warned about to the agent.” — index.ts:2727-2733

O modo de falha que ninguém pega não é o conflito: é o não-conflito. Dois agentes editam hunks disjuntos do mesmo barrel, roteador ou union de tipos, o git mergeia limpo, e sai código que nenhum dos dois pretendeu. E o schema não tem onde declarar write-set.

O corpo do loop de merge de uma etapa é, na íntegra (integration-merge.ts:40-71): filtra pending, loga, chama git.merge, empurra pra branchesMerged. Sem typecheck, sem teste, sem build, sem lint, sem hook, sem nem um git status de sanidade. O único critério de sucesso é o git ter saído 0.

Com um merge dentro do gate, um vermelho nomeia o card; com quatro, não nomeia nada. A bissecção é o produto, não a limpeza.

E a durabilidade: working-on-orchestrator/SKILL.md:70 afirma que o RunManifest “is written incrementally during the run”. É falso — RunLogger.flush é chamado uma vez, no finally. Um SIGKILL no meio de uma etapa deixa zero artefato em .huu/. O trabalho está nos branches; recuperável só à mão.

Duas ironias medidas

Constrói pro cliente o que não usa em si

O pipeline huu Knowledge System termina com um eval de roteamento cego para as skills que ele gera. A biblioteca de 20 skills que governa o próprio repo não tem eval nenhum. E docs/ci.md (245 linhas) ensina, com receita pronta de GitHub Actions, a rodar as auditorias do huu em CI — num repositório sem .github/.

O $hint é um canal de injeção

O playbook de prompts manda “fence the injected $hint inside its own tagged block so the model never treats scanned data as orders”. Em 7 de 7 pipelines o $hint é interpolado como prosa de instrução, sem escape — e ele é texto escrito por um LLM (o step de recon), limitado apenas por um truncamento de 600 chars.

A prova por mutação

Tudo no diagnóstico é leitura de código. Isto é experimento: quatro mutações aplicadas ao fonte, suíte inteira rodada, código restaurado. A suíte tem 1.786 testes passando em 13,3 s — velocidade nunca foi desculpa.

Leia a mutação 1 devagar. Os dois guardas de maxNodeExecutions são a única coisa entre um outcome de CheckStep apontando para trás e um loop de gasto de LLM ilimitado. Apagar os dois deixa o gate inteiro verde.

A mutação 2 é pior do que “morta”. O único teste que a pegou tem por propósito o tratamento de falha de merge: ele stuba merge para falhar no callCount === 1 e asserta que o agente 1 é o perdedor. A ordem é pega como efeito colateral de uma fixture. Reescreva aquele stub para chavear por nome de branch — a refatoração mais natural do mundo — e o invariante fica indetectável. A mutação 4 já prova isso para o sort em si.

O fan-in é onde os fornecedores param3-0

Todo produto enviado transforma o merge-back num funil explícito acionado por humano: /apply-worktree, Apply-or-discard, e o /best-of-n que declara literalmente que “does not merge changes back … for you”.

Ou seja: o merge determinístico de N branches ao fim de cada etapa — o diferencial nº 1 do MANIFESTO — é genuinamente distintivo, e é exatamente o passo que nenhuma fonte externa valida. Corta nas duas direções: o manifesto está certo, e o componente mais original do produto é o menos verificado — zero verificação entre merges, zero arquivo de teste em integration-merge.ts.

A academia já nomeou o defeito3-0

arXiv:2606.15376 (CoAgent, SJTU, jun/2026) sobre orquestração fork-and-merge: “weak isolation akin to read committed”; um merge em nível de linha “catches textual conflicts but nothing beyond — the merged code can fail to even compile.” É a formulação acadêmica da frase que o diagnóstico derivou do código.

Admissão: fail-fast numérico, não fila3-0

O Claude Code usa portões numéricos duros com erros “não-retentar”: 20 spawns concorrentes, 200 por sessão. O huu faz o oposto por decisão bem-fundamentada (o incidente de OOM). Não troque o pacing pelo fail-fast — mas copie o que falta: um teto absoluto, por sessão, que não depende de nenhum sinal dinâmico funcionar.

O que a pesquisa NÃO confirmou — e por que isso não é “falso”

Dos cinco ângulos, três não produziram nenhuma afirmação sobrevivente: verificação de código gerado por agente (falso-verde, mutação, LLM-as-judge, benchmarks); quase toda a economia de contexto e memória; e praticamente tudo de PSI/AIMD, caching, roteamento por papel e OpenTelemetry para agentes.

  1. Ausência de literatura secundária ≠ refutação. O ROADMAP.md já cita fontes primárias — docs do kernel, TMO (ASPLOS'22), senpai/oomd da Meta, concurrency-limits da Netflix. A pesquisa não achou ninguém escrevendo sobre aplicar isso a fleets de agentes de código. Conclusão honesta: o huu está fazendo algo que a indústria ainda não documentou, e a validação vai ter de ser própria. É uma boa posição — sem rede.
  2. Para o ângulo da verificação, a ausência é mais interessante ainda: este trabalho produziu a evidência que a pesquisa não achou. As quatro mutações, os dois erros plantados, o teste cruzado dos gêmeos e as 14 citações conferidas são medição de primeira mão. O catálogo de falso-verde é, na prática, um artefato original.
  3. Nada aqui deve ser preenchido com plausibilidade. Se a verificação não sustentou, entra no ledger como ABERTO, com o teste que fecha — não no corpo do método.

Padrão de escrita de um gate

### GATE <ID> — <a asserção em uma frase, no afirmativo>

<Por que existe: o dano CONCRETO se for pulado. Não "boas práticas".>

Antes de <ação>, numa sessão com <quem, por papel>:
1. <comando executável, literal, copiável>
2. <como confrontar o resultado com o artefato do repositório>
3. **Registrar o resultado em <caminho de ADR nominal>** — item a item, com o
   veredito (igual / divergente / NÃO_COLETADO) e o que muda se divergir.

- [ ] <artefato de saída> existe e cobre todos os itens
- [ ] Toda divergência corrigida **e** as fixtures recapturadas

Os quatro elementos obrigatórios: condição de entrada · evidência exigida (saída de comando salva, nunca afirmação) · artefato nominal onde a evidência mora · quem assina, por papel nomeado — nunca “o time”.

Um veredito que não pode existir: CONFERE sem evidência anexada. Use NÃO_COLETADO, que nunca vira CONFERE sozinho.

A regra dos hooks: separe nudge de gate

Prosa numa skill é conselho; um hook é garantia.

O huu tem zero hooks e duas peças prontas e desligadas. A tentação é ligar tudo. A regra que evita o desastre: gate mecânico só onde o erro é irreversível ou auto-amplificante — memória persistida, segredo, história do git. Nudge para o resto. E diga, no próprio arquivo, qual é qual.

  • Todo hook falha ABERTO — um hook quebrado reporta em vez de inutilizar a sessão.
  • Escopo estreito o bastante para não ser desligado. Uma proteção que dispara em trabalho comum acaba desligada, o que é pior que não tê-la. E o corolário: um gate que só pode ser satisfeito contornando-o ensina a contornar.
  • O nudge é honesto sobre si mesmo — escreve no próprio texto que é lembrete, não garantia, e aponta onde vive o enforcement.

Para este repo, os quatro certos: gate de escrita da memória (bloqueia edição de SKILL.md sem token verde, TTL 30 min — um verde de 30 minutos atrás não autoriza mais uma escrita); gate de segurança; gate de encerramento (o script que já existe e ninguém ligou); e nudge de roteamento (~130 tokens, porque AGENTS.md é lido uma vez e sai de atenção numa sessão longa).
