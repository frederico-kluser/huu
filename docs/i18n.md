# Internationalization

huu ships in **English** (`en`, the default) and **Brazilian Portuguese**
(`pt-BR`). Both front-ends — the Ink terminal UI and the browser UI — read the
same catalog, and so do the CLI's `--help`, banners and errors.

## Picking the language

| Surface | How |
|---|---|
| CLI + terminal UI | `HUU_LANG=pt-BR huu` — or `HUU_LOCALE`, or the POSIX chain `LC_ALL` → `LC_MESSAGES` → `LANG` |
| Web UI | ⚙ **Settings → Language**. Saved per browser in `localStorage` (`huu.lang`); switching repaints the page without a reload |

Anything unrecognised falls back to `en`. `pt`, `pt-PT` and `pt_BR.UTF-8` all
resolve to `pt-BR`; `en-GB` and `en_US.UTF-8` resolve to `en`.

## A missing translation is an error, on purpose

The contract is that huu never renders a half-translated screen. It is enforced
at three layers, so a hole cannot survive to a user:

1. **Compile time.** `en` is the source catalog: its keys define `MessageKey`,
   and `pt-BR` is typed `Record<MessageKey, string>`. Add a key to `en` without
   its twin and `npm run typecheck` fails, naming the key.
2. **Boot.** Every entrypoint calls `initI18n()`, which runs
   `assertCatalogsComplete()`. A key that is absent, empty, orphaned, or whose
   `{placeholders}` drifted between locales aborts the process with
   `CatalogIntegrityError` before the first frame is drawn.
3. **Call site.** `t()` and `translate()` throw `MissingTranslationError` the
   moment a key is missing from **any** shipped locale — including one the user
   is not currently running. An English-only key must not survive just because
   nobody switched to `pt-BR`.

On top of that, `src/lib/i18n/coverage.test.ts` walks the source, collects every
key the app references, and fails the suite on an untranslated reference or an
orphan catalog key.

**Escape hatch:** `HUU_I18N_STRICT=0` downgrades layers 2 and 3 to a stderr
warning and renders the raw key. It exists for operators who would rather ship a
rough string than stop; the default is strict.

## Adding a key

1. Add it to the right module under `src/lib/i18n/locales/en/` — `common.ts`
   (shared verbs, status codes), `cli.ts`, `tui.ts`, `tui-run.ts`,
   `tui-editor.ts` or `web.ts`.
2. Add the same key to the `pt-BR` twin. `npm run typecheck` tells you if you
   forgot.
3. Use it:
   - **TUI / CLI / server** — `import { t } from '../lib/i18n/index.js'`, then
     `t('tui.home.menu_quit')`. The key is typed, so a typo is a build error.
   - **Browser JS** — `import { t } from '../i18n.js'`, same call shape.
   - **Browser markup** — `data-i18n="web.settings.title"` on the element
     (`-html`, `-placeholder`, `-title`, `-aria-label` variants also exist).
4. Interpolate with `{name}` slots: `t('tui.dash.retry_prompt', { id: 7 })`. A
   slot with no matching parameter throws `MissingParamError`.

For a key assembled at run time (`status.${code}`), use `translate()` — same
guarantees, no compile-time check — and register its prefix in
`DYNAMIC_PREFIXES` inside `coverage.test.ts` so the orphan check stays honest.

## What is deliberately NOT translated

- **Pipeline data.** Scaffold step names and prompts in the pipeline editor are
  handed to an LLM, not shown as chrome. They stay in English so a pipeline
  behaves identically whatever language the author's UI was in.
- **Classifier codes.** `src/lib/card-state.ts` and its browser mirror
  `src/web/client/card-state.js` return stable English codes (`NO CHANGES`,
  `READY`). They are pure, mirrored and pinned by tests; the translation happens
  at the render boundary via `tStatus()` (Ink) and `phaseLabel()` (web).
- **Brand and protocol names.** `OpenRouter`, `Azure AI Foundry`, `git`,
  `worktree`, env var names, CLI flags.
